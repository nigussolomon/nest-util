# General Preferences
- Prefers opt-in features with backward-compatible defaults — new behavior is off by default and must be explicitly enabled; existing code paths must be preserved until a developer consciously opts in. Confidence: 0.90
- Prefers fail-closed security mechanisms — when a security check cannot be performed (e.g., no authenticated user), deny access (403) rather than silently allowing it. Confidence: 0.85
- Prefers returning 404 (Not Found) rather than 403 (Forbidden) when a resource exists but the requesting user does not own it, to prevent existence leaks (attacker cannot distinguish "doesn't exist" from "not yours"). Confidence: 0.80
- Prefers detailed, structured implementation plans written before coding — plans include specific file paths, type signatures, function signatures, line-number references, and explicit behavior tables. Confidence: 0.85
- Prefers documentation (SKILL.md, MIGRATION-GUIDE.md) to be updated as part of the implementation itself, not as a separate follow-up task. Confidence: 0.75
- Prefers comprehensive test matrices covering all scenarios — owned, not-owned, bypass-via-permissions, bypass-via-predicate, unauthenticated, enforcement-off, and variant configurations — for every affected endpoint. Confidence: 0.75
- Prefers extracting shared logic into private helpers rather than duplicating code across methods (e.g., `applyOwnershipCondition`, `applyIncludeJoins`). Confidence: 0.70
- Uses `pnpm` as the package manager and runs tests via `pnpm nx test <project-name>` (not `npx jest` or `npx nx test`). Confidence: 0.80
- Prefers granular, distinct permission action names over coarse/overloaded ones — e.g., `findAll` → `read` and `findOne` → `readOne` as separate defaults rather than both mapping to `read`. Confidence: 0.70
- Prefers uniform security enforcement across all CRUD endpoints — if ownership is enforced on read/update/delete, it must also be enforced on create; no endpoint should be an unprotected backdoor. Confidence: 0.75
- Prefers using existing lifecycle hooks (e.g., `beforeCreate`, `beforeUpdate`) as the escape hatch for complex custom logic rather than adding new configuration options to cover edge cases — each config option keeps a narrow, strict contract and doesn't stretch to accommodate every use case. Confidence: 0.65
- Configures `userOwnershipField` with the entity relation property name (e.g., `user`) rather than the database foreign-key column name (e.g., `userId`), and expects the library to handle the FK-to-relation mapping internally — consistent across ~90% of services. Confidence: 0.60
- Prefers fixing input data so existing processing pipelines run naturally with correct values, rather than adding special-case skips or field deletions to work around downstream logic — when enforcing ownership on create, set both the entity property and the FK column so `resolveRelations` resolves the correct entity without any bypass. Confidence: 0.65
- For ownership enforcement on create (both plain column and relation-backed): if the client provides an ownership value that doesn't match the authenticated user's ID, throw 404 (Not Found) rather than silently overwriting. Silent auto-fill should only happen when the value is missing/absent from the payload. This extends the "no existence leaks" principle to create operations and applies uniformly regardless of whether the ownership field is a plain column or a relation. Confidence: 0.80
- Uses `~go` as a shorthand command to approve the current plan and tell the assistant to proceed with implementation (equivalent to "exit plan mode and implement"). Confidence: 0.65
- Prefers reusing existing infrastructure patterns when adding similar adjacent features rather than building parallel/duplicate subsystems — e.g., registration OTP verification deliberately reuses the same `OtpDeliveryCallback` type, `generateOtpCode()`, bcrypt hashing, and attempt-tracking patterns from login OTP rather than introducing a separate verification delivery mechanism. Confidence: 0.70
- When edge cases or security concerns are surfaced during implementation (e.g., race conditions, squatting attacks), prefers documenting them as TBD rather than immediately expanding scope to fix them — defers to a later pass unless explicitly asked to implement now. Confidence: 0.60
- Prefers explicit `git add` with specific file paths over blanket `git add .` / `git add -A` — staging should be intentional and auditable, and the assistant should list every changed file rather than using catch-all commands. Confidence: 0.65
- Prefers conventional commit messages with scoped packages, version-bump annotations, and detailed per-package bullet-point breakdowns in the body (e.g. `feat: create ownership enforcement, relation FK fix, and registration OTP verification` with `nest-crud (1.0.9 → 1.1.0):` subheadings). Confidence: 0.65
- Prefers thorough pre-commit verification — checking what's already committed vs. uncommitted, listing untracked files, reviewing the diff stat, and running a post-commit `git status` to confirm a clean state before reporting "ready to push." Confidence: 0.60
- Prefers nesting feature-specific configuration under the feature's own config namespace (e.g., `approvalPipeline.hooks`) rather than adding top-level `CrudServiceOptions` fields — keeps options scoped/colocated with the feature they belong to and consistent with sibling options like `permissions`/`visibleStatuses`. Confidence: 0.70
- When a plan has ambiguous design decisions, prefers them surfaced as explicit questions with the user's own stated recommendation, and expects the assistant to address each question directly (adopt the recommendation or justify a deviation) in its final summary. Confidence: 0.60
- Prefers documentation written as easy-to-understand, beginner-friendly guides — with numbered quick-start steps, copy-pasteable code examples, overview tables, and "try it" snippets — rather than dry API references. Confidence: 0.75
- Prefers documentation that comprehensively covers the whole codebase and accurately reflects the actual code (current package versions, public exports, real app wiring), rather than going stale or drifting from the implementation. Confidence: 0.65
- Maintains documentation in multiple mirroring formats (markdown README + per-package HTML pages) and expects changes to be propagated to every format to keep them in sync, not just the primary markdown source. Confidence: 0.70
- Prefers every package in the monorepo to have its own dedicated HTML docs page matching the same layout/structure as sibling packages (consistent sidebar, nav, and content sections), rather than some packages pointing to a GitHub README or lacking a local page. Confidence: 0.70
